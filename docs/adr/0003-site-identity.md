# ADR 0003: organization-owned site identity

Status: candidate, 2026-09-29.

An organization is the authorization tenant. A site is a distinct website within one organization and has its own UUID, display name and normalized origin. Existing forms remain unassociated (`siteId: null`) until a user assigns them. Go owns sites and the form association. The control plane resolves a human membership to an organization but cannot infer a site from that organization ID.

`POST /v1/sites` requires `forms:write`; list and get require `forms:read`. The origin is an HTTPS origin with no path, credentials, query or fragment. HTTP is accepted only for `localhost`, `127.0.0.1` or `[::1]` development origins. Hostnames are lowercased and converted to ASCII, trailing DNS dots and default ports are removed. The unique `(organization_id, origin)` constraint is the concurrency authority. A retry with the same normalized origin and display name returns the existing site as 200 and the same ID. A request using that origin with a different name returns 409. This is narrow reconciliation for site creation, not general idempotency across all operations. A caller facing an uncertain response can list or get the site and compare its origin and name before continuing.

Forms may supply a `siteId` on creation or metadata update. The repository checks site ownership inside the mutation transaction. A composite `(organization_id, site_id)` foreign key makes the same-organization rule hold for every database writer. Foreign site IDs return not found without disclosing another tenant's site. Site association does not grant submission-read permission, and no new submission access path is introduced here. Cross-form inbox reads, site filters and site deletion are separate decisions.

The production runtime role has site select and insert only. Existing forms remain valid through the nullable column. The down migration takes exclusive locks on sites and forms and refuses to run while any site identity exists. Operators must preserve or migrate those identities and stop writes before a later rollback; the database check and schema removal execute in one transaction.

A `siteId: null` form metadata patch explicitly clears an association. `GET /v1/sites` includes `meta.organizationId` from the authenticated principal, even for an empty result, so a client can verify its selected organization before attempting any write. A failed populated down migration may mark the `golang-migrate` version dirty. Operators must first preserve or migrate site data and confirm write quiescence, then inspect the actual schema and `schema_migrations` state. Only after confirming which migration effects remain may they use `migrate force <verified-current-version>` and retry the rollback. No automatic force or destructive cleanup is part of the rollback path.
